Introduction

  1. Introduction. You will be writing a virtual machine to emulate the RISCV32IMA instruction set architecture (ISA). The RISCV32IMA(Zicsr)(Zicntr) specification means:

    1. RV32. It’s going to be the RISCV, 32-bit instruction specification.

      1. Register Size. The integer registers are prefixed with an x and are 32 bits wide. The program counter is also 32 bits wide.

    2. RV32I. It’s going to include all integer instructions.

    3. RV32M. It’s going to include multiplication and division instructions.

    4. RV32A. It’s going to include atomic memory operation (AMO) instructions.

      1. Alias. RV32A implies two extensions: (1) Zaamo and (2) Zalrsc.

      2. Zaamo. You will implement atomic instructions: amoswap, amoadd, amoand, amoor, amoxor, amomax[u], amomin[u].

      3. Zalrsc. You will implement Load-Reserved and Store-Conditional LR and SC.

      4. You do not need to implement any other atomic instructions.

    5. Zicsr. It’s going to include some control and status registers (CSR), but you will need all six (6) CSR instructions (csrrw, csrrs, csrrc, csrrwi, csrrsi, and csrrci).

    6. Zicntr. It’s going to support base counters and timers.

    7. Instructions Reference. See RISC-V Reference Manuals for the RISC-V reference manuals.

  2. VM Process. Your virtual machine will read an ELF file then fetch, decode, execute, go to memory, and write the result of each instruction.

    1. Multithreaded Pipeline. Each one of the five stages of the pipeline will be in its own thread.

Machine Memory

  1. Initial Memory. Allocate memory for your machine. The amount of memory will be specified by the mem configuration key.

    1. Initial Value. The initial memory will be left uninitialized. Do not put values into memory until the ELF part.

  2. Memory Addresses. The physical memory address will be the index into this allocation.

    1. Example. Memory address 0 is at the very beginning of the allocation. Memory address 0x1F starts at index 31.

  3. Program Memory. The second step is to read the ELF file into the machine’s memory which you will do in the next part.

  4. Virtual Memory. ALL memory accesses will first check the SATP register, including instruction fetches, loads, and stores. If SATP.MODE=0, then the memory address is untranslated. Otherwise, if SATP.MODE=1, your MMU must translate the virtual address into the physical address. Recall physical addresses are the indices into the RAM allocation array.

    1. Translation Lookaside Buffer. You will be implementing a translation lookaside buffer (TLB). The SATP register must be checked before the TLB is accessed to make sure SATP.MODE=0.

      1. Eviction Policy. You will use the least-recently used (LRU) eviction policy for the TLB.

      2. Table Rows. The TLB rows will contain five parts: the physical page number (not the full address), the virtual page number (not the full address), the page size as a leaf level (e.g., 1 = 4MiB, 22 bits, and 0 = 4KiB, 12 bits), the access bits R, W, X, U, G, A, and D, and finally, a field to support the eviction policy (i.e., FIFO position, hit count, or global timer count).

      3. Physical Page Numbers. A physical address is always 34 bits, but you will only store the page number. For a leaf at level 1, you will store only the upper 12 bits (PPN[1]). For a leaf at level 0, you will store the upper 22 bits (PPN[1:0]). The last 12 bits of the physical address is never stored.

      4. Virtual Page Numbers. The virtual address is always 32 bits, but just like the physical address, you will only store the page number. For a leaf at level 1, you will store only the upper 10 bits (VPN[1]), and for a leaf at level 0, you will store the upper 20 bits (VPN[1:0]). The last 12 bits of the virtual address is never stored.

    2. Access Faults. Always check the bounds of RAM before giving a physical address. Any out-of-bounds physical addresses will cause an access fault. Access faults will immediately park the HART and the status can be read via the hart_status system call. The HART can be restarted using the start_hart system call.

    3. Page Faults. The MMU can trigger one of three page faults: (1) Store/AMO page fault, (2) Load page fault, and (3) Instruction page fault for STORE or atomic memory operations, LOAD, and instruction fetches, respectively. Page faults will be handled just like access faults. This means the faulting HART will park, and the reason can be queried via the hart_status system call.

      1. Causes. The MMU will page fault for the following reasons: (1) a page table entry’s Valid bit (index 0) is cleared to 0, (2) there is not a leaf by level 0, or (3) the R, W, or X bit is cleared for a load, store, or instruction fetch, respectively.

Registers

  1. Integer Registers. There are thirty-two (32) integer registers in RISC-V.

    1. Register File. The integer registers are per-HART, meaning every HART in your machine will have the same number and type of registers.

    2. Read/Write API. You will need a read/write API to support the registers.

      1. Zero Register (x0). The first register at index 0 is the zero register. Any reads from this register always gives 0. Any writes to this register discards the write.

  2. Program Counter. You will also need to add the program counter register for each HART., Except with a jump or a branch instruction, the program counter will always add 4 after each instruction since each instruction is exactly 4 bytes.

    1. Initial PC. The program counter will eventually be initialized with the entry point address specified in the ELF file.

    2. Stack Pointer. The start code in the library will set the stack pointer. Your machine will leave it uninitialized per HART.

Read-only CSRs

  1. Illegal Instruction Error. Writing to a read-only CSR will trigger an illegal instruction and park the HART.

  2. HART Restarts. The HART can be restarted using the start_hart system call.

  1. Cycle Counter. You will maintain a cycle counter for each HART.

  2. Cycle Frequency Configuration. The cycle speed is configurable frequency via the -hz switch.

  3. Per-HART Cycle Counter. Each HART will count the number of cycles it has executed.

  4. Stalled or Parked HART. When the program counter (PC) is frozen for any reason (such as a pipeline stall or the HART is parked), the cycle counter will not increase.

  2. Per-HART. This register is still per-HART, but for the most part, they all return the same value at the same time.

  2. Flushed Instructions. Instructions that are flushed from the pipeline due to a branch misprediction will still count towards the cycle count for that particular HART.

Sign Extension

    1. Example. For a short, the sign bit is at bit index 15, whereas for an I-type instruction, the sign bit is at bit index 11.

  2. Sign Extension Function. You must create a function that takes a value and the location of the sign bit. The function must extend the value to 32 bits.

    1. Restrictions. Your sign extension function must NOT contain:

      1. loops (do/while/for)

      2. conditionals (if/else)

Cache

  1. Cache Levels. Your machine must support up to level 3 cache.

  2. Per-HART Cache. Levels 1 and 2 will always be per-HART.

  3. Global Cache. Level 3 will always be shared for all HARTs.

  4. Coherency. Cache coherency can be specified by the cC key to use none, snoop, or dir for no coherency, snooping coherency, or directory coherency, respectively.

    1. Protocol. You will use the Modified, Exclusive, Shared, Invalid (MESI) protocol.

Because L3 is shared across HARTs, main memory and it are your primary source of cross-thread contention. Guard it carefully; see Multithreading and Locking.

Branch Predictors

  1. Branch Target Buffer. If turned on, there will be a branch target buffer for every HART with the number of slots in each specified by the configuration -bp switch.

  2. HART Configuration. The configuration of the buffer will be the same for every HART.

  3. Table Specification. The branch target buffer will hold the memory address of the branch instruction itself and the 2-bit history of the branch.

  4. Default Prediction for Compulsory Misses. On a branch target buffer compulsory miss (i.e., the branch instruction has not been seen before), you will put the default branch prediction in the table.

SATP Register

  1. SATP when MMU is Disabled. The SATP register is a CSR that can be hardwired to 0 if the -mmu switch is set to off.

    1. SATP Hardwired to 0. In this configuration, SATP will always be 0 no matter what is written to it.

  2. Default SATP State. If the MMU enabled, either specifically or by default, then SATP will start as 0, but it can be turned on by software.

    1. SATP Modes. Recall MODE is bit index 31 which can be 0 (BARE mode) or 1 (SV32 mode).

Pipeline Stages

  1. Two-Phase Pipeline Clock. All five (5) pipeline stages will have two functions: (1) rising_edge and (2) falling_edge.

    1. Rising Edge Clock. On the rising edge of the global clock, the rising_edge function will be called to completion.

    2. Falling Edge Clock. Then, on the falling edge of the global clock, the falling_edge will be called to completion.

  2. Cycle Speed. The rising edge and falling edges will both be completed within the configured 1/Hz or the instruction speed, whichever is slower.

    1. Errors. Cycle speeds that are too fast will not cause errors slow instructions will run to completion regardless of the speed of Hz.

  3. Read on Rising Edge. Recall that the rising edge of the clock is where the source operands are loaded and most of the stage is completed.

  4. Write on Falling Edge. The falling edge is where the intermediate registers, which are the registers in between each pipeline stage, take their new values.

Two-Phase Clock and Intermediate Registers

Think of one clock tick as two ordered phases that every stage observes in lockstep:

  1. Rising edge (compute). Each stage reads the intermediate register on its input side (the value latched by the previous stage on the last falling edge) and computes its result into a private "next" buffer. Nothing that another stage can observe changes during this phase.

  2. Falling edge (latch). Each stage copies its "next" buffer into the intermediate register on its output side. This is the only phase in which the visible pipeline state advances.

  3. Double Buffering. A stable "current" latch that is read, plus a "next" buffer that is written is the single most important structural decision in the project.

  4. Mutual Exclusion. If every stage reads only "current" latches on the rising edge and writes only "next" buffers, then latches into "current" on the falling edge, no two stages ever touch the same live value at the same time, which is what makes the multithreaded design tractable.

    1. Example. See Multithreading and Locking.

Clocking on Register File

The integer register file follows the same two-phase clock as the intermediate pipeline registers.

  1. Decode on Rising Edge. The decode stage reads an integer register on the rising edge.

  2. Write on Falling Edge. The writeback stage writes an integer register on the falling edge.

  3. Mutual Exclusion. Because reads and writes are separated into different phases, decode and writeback within one HART never race on the register file.

  4. Hazards. The trade-off is that a producer’s result is not visible to a later dependent reader until the end of the producer’s writeback cycle, which is what creates data hazards.

    1. Example. See Pipeline Hazards.

Multithreading and Locking

Each of the five stages runs in its own thread, and you may have up to sixteen HARTs, so a naive design can easily deadlock or produce non-deterministic, and hence ungradeable, output.

Follow these guidelines:

  1. Synchronize the two phases with a barrier. Create a barrier that all stage threads (per HART) rendezvous on twice per clock: once at the end of the rising edge and once at the end of the falling edge. A barrier (C++ std::barrier, Java CyclicBarrier/Phaser, C# System.Threading.Barrier, Rust std::sync::Barrier) guarantees no thread starts the next phase until every thread has finished the current one.

    1. Determinism. Using barriers and locking turns the whole simulation into a deterministic, repeatable machine, which you want for both debugging and grading.

      1. Cycle Speed. This determinism is the reason that your cycle speed is the slower of 1/Hz or the host instruction itself.

  2. Prefer phase separation over fine-grained locks. If every shared latch is only read during the rising edge and only written (into a separate buffer) then swapped during the falling edge, the barrier alone provides all the mutual exclusion you need for per-HART pipeline state.

Reach for locks only for state that is genuinely shared across HARTs.

  1. Lock the shared structures. The following are shared and must be protected:

    1. Shared L3 cache. Guard with a mutex. To reduce contention, consider one lock per set rather than one global cache lock.

    2. Main memory. Guard with a mutex or a reader/writer lock (many concurrent readers, exclusive writers).

    3. Coherency traffic. Snooping (MESI) requires a serialization point. Model the "bus" as a lock so that at most one coherence transaction is in flight at a time. A directory (dir) can use a per-line lock instead of a global bus lock.

    4. Standard I/O. putchar/getchar syscalls from different HARTs must not interleave a single character’s worth of I/O; guard STDOUT/STDIN with a lock.

  2. Always acquire locks in a fixed global order, The simplest deadlock-free rule for the cache hierarchy is to acquire outer to inner: L1 → L2 → L3 → RAM, and never the reverse. When locking by address (e.g., AMO or a cache set), acquire in ascending address/index order. Document your ordering in BUILD.md.

  3. Use RAII / scoped locks. Prefer std::lock_guard/std::scoped_lock (C++), synchronized/try-finally (Java), and lock (obj) { …​ } (C#) so a lock is released even on an early return or exception.

  4. Make AMO instructions truly atomic. An RV32A read-modify-write must appear indivisible to other HARTs. Implement it by holding the memory (or target cache-line) lock across the entire load-modify-store, or by backing the operation with a language atomic (std::atomic, java.util.concurrent.atomic, Interlocked, std::sync::atomic).

    1. Load-Reserved/Store-Conditional. For the LR and SC instructions, track the reservation set and invalidate it on any conflicting write.

  5. Do not busy-wait. Spinning on a flag wastes CPU and can starve other stage threads. Use the barrier and, where you must wait for a condition, a condition variable rather than a spin loop.

A common bug is a stage thread that reads a latch another stage is currently writing. If you ever see this, it almost always means you wrote directly into a current latch during the rising edge instead of into a next buffer. Re-check the double-buffering discipline before adding locks.

ELF Reading Sequence

  1. Error Checking. You first need to see if the ELF file is legitimate. You do not want to load an ELF file that is not for your specific machine.

      4. e_bitsize. check that the file is for a 32-bit architecture by checking e_bitsize.

  2. Program Table. After the ELF file is verified, you need to start loading it by seeking to the program table. The program table includes a header (PH), which you will need to read.

    1. p_type. check that p_type is PT_LOAD. Skip any segment that is not loadable.

    2. p_offset. seek in the ELF file to the byte offset given in p_offset.

    3. p_vaddr. copy p_filesz bytes from the file (starting at p_offset) into memory starting at address p_vaddr.

    4. Zero-fill. If p_memsz is greater than p_filesz, set the remaining p_memsz - p_filesz bytes in memory (immediately after the copied data) to 0. This is how the .bss segment is created.

  3. Entry Point. Finally, when all of that is copied, the entry point address (e_entry in the ELF header) needs to be set in the program counter register (read below).

Copy exactly p_filesz bytes from the file, never p_memsz. Copying p_memsz bytes reads past the segment’s on-disk data and corrupts memory. The extra p_memsz - p_filesz bytes come from zeroing, not from the file.

Part III: Fetching

  1. Submit File. Write your fetching code in its own source code file. You will submit it by itself.

  2. Instruction Size. All instructions in the RV32IMA instruction set are 32 bits (4 bytes), and for this project, the bytes will be in little endian.

    1. Fetch Sequence. You will need to read four bytes starting at the program counter, which is initially set to e_entry from the ELF header.

    2. Instruction Counter CSR. You will need to increase the instruction counter register for the HART by one (1).

  3. Two-Phase Pipeline Stage. Your instruction fetch reads the PC and instruction on a rising-edge. It then writes the 32-bit instruction to its intermediate register, which is the input to the decode stage.

  4. Virtual Memory. You must use your memory seam to find the instruction since it may be in virtual memory, and hence, your MMU must translate it.

    1. Page Fault. If the fetch cycle faults, it will park the HART. The HART may be restarted by software by using the start_hart system call.

      1. Cause. You must keep track of what caused the HART to park. This status can be read by the software through the hart_status system call.

  5. Instruction Structure. Use the instruction structure given below.

  6. Incremental Use of Fields. All fields will be used after all five stages are implemented. You will continually use more and more fields, but for the fetching portion, you will only use the inst field.

  7. Branch Prediction. Your fetcher will have a 2-bit branch prediction table.

    1. Format. The branch prediction table will store the branch instruction’s PC address.

    2. 2-bit. The branch prediction table will also store the 2-bit branch as not taken (0) or taken (1) as a shift register.

      1. Grading. You MUST implement this as a shift register. It must not be a list of if or switch statements.

Decoding Operands

  1. Decode Stage. The decode stage needs to load both operands.

    1. R-Type. For R-type instructions, both operands come from the register file.

    2. I-Type. For I-type instructions, the left operand comes from the register file, and the right operand comes from the 12-bit immediate encoded in the instruction, sign extended to 32 bits.

    3. U-Type. There are two U-type instructions, LUI and AUIPC.

      1. LUI. The LUI instruction adds the upper immediate to the value 0 for the ALU operation.

      2. AUIPC. The AUIPC instruction adds the upper immediate to the program counter (memory address) of the AUIPC instruction itself.

    4. S-Type. The S-type instruction needs to use left/right as inputs to the ALU to calculate the memory address, which is comprised of the register value plus the offset (sign extended to 32 bits). The value of that needs to be stored comes from the register file, but it is stored in the strval field in the structure.

      1. Register Meaning. The stored value is in rs2, and the base memory address is in rs1.

    5. B-Type. The B-type instruction is kind of like the set-on-less-than set of instructions, except that the result determines what is added to the program counter in the writeback stage.

    6. J-Type. The J-type instruction is an unconditional addition to the program counter, which is the sign-extended 21-bit immediate (sign extended to 32 bits) added to the current program counter. The ALU will not perform any actions.

      1. Jump and Link to Register (JALR). JALR (jump-and-link-to-register) is an I-type, not a J-type instruction.

  2. Relative PC. All B-type and J-type instructions are PC-relative. This means that the immediate is directly added to the program counter of the branch or JAL instruction.

  3. Sign Extension. By default, all immediates encoded in instructions are sign-extended. The sign bit for ALL instructions is located at bit index 31, which is the most significant bit of the 32-bit instruction.

Part V: Executing

  1. Submit File. Write your executing code in its own source code file. You will submit it by itself.

  2. Execute Stage. The execution stage is the ALU stage.

    1. Input. Your ALU will take the aluop field and perform that operation.

    2. Result. The result will be stored in result.

  3. Branch Prediction. The execute stage is where you can verify your branch predictor. See Control Hazards (branches and jumps) below.

  4. Load and Store. For the LOAD and STORE instructions, the ALU will calculate the memory address plus offset. This will be done via the aluop ADD. The ALU does not look at the instruction.

  5. Operand Forwarding. The execute stage is where operand forwarding resolves.

    1. Identifying RAW Hazard. Immediately before running the ALU, check whether a more recent (not-yet-written-back) instruction produces one of this instruction’s source registers.

    2. Resolving RAW Hazard. If you detect the situation above, substitute that forwarded value for the stale value read from the register file. See Pipeline Hazards.

  6. Status Flags. The ALU will also produce four status flags: NZCV for negative, zero, carry, and overflow, respectively.

Comparisons for the set-on-less-than or branch instructions are done by taking the difference of the two operands and inspecting the result.

Computing the NZCV Flags

The cleanest way to produce all four flags is to route every additive operation through one wide (at least 33-bit) unsigned addition and read the flags off that single result. Treat subtraction as an add of the two’s complement: a - b = a + (~b) + 1. Because BRANCH and the set-on-less-than instructions all use the Sub op, this one code path answers every comparison.

Let a and b be the 32-bit operands, and compute the sum in a wider unsigned accumulator so the 33rd bit survives:

  • ADD: wide = (uint64)a + (uint64)b

  • SUB: wide = (uint64)a + (uint64)(~b) + 1 (equivalently (uint64)a + (uint64)(uint32)(-b))

Let r = (uint32)wide be the 32-bit result. Then:

Flag How to compute

N

Sign bit of the result: (r >> 31) & 1.

Z

Result is zero: r == 0.

C

Carry/borrow out of bit 31: (wide >> 32) & 1. For Sub, a carry-out of 1 means no borrow, i.e., a >= b when both are treated as unsigned.

V

Signed overflow. For Add: ~(a ^ b) & (a ^ r >> 31) & 1. For Sub: (a ^ b) & (a ^ r >> 31) & 1.

Once the Sub op has set NZCV, every branch and set-less-than is just a combination of flags. No second comparison is needed:

Pin down your carry convention and never reverse it. This document defines C from subtraction so that C == 1 means "no borrow" (a >= b unsigned). If you instead treat C as the raw borrow bit, every unsigned branch (BLTU/BGEU) and SLTU silently inverts, which is a miserable bug to find late in the semester. Compute C one way, write a unit test for BLTU/BGEU at the 0xFFFFFFFF boundary, and leave it alone.

Part VI: Memory

  1. Submit File. Write your memory code in its own source code file. You will submit it by itself.

  2. Load and Store. The memory stage is only used for AMO, LOAD, and STORE instructions.

    1. AMO. Atomic memory operations read-modify-write memory where only the write is visible to other HARTS. In other words, the memory operations cannot be interrupted.

    2. Store. The STORE instructions will use the strval value to store to the memory address calculated by the ALU and stored into result.

    3. Load. The LOAD instruction will take the result, load the value from memory, and store the value from memory into result.

      1. Sign Extension (signed). The lb and lh instructions will sign-extend to fill the 32 bits.

      2. Zero Extension (unsigned). The lbu and lhu instructions will zero-extend to fill 32 bits.

  3. LOAD Result Overwrite. Overwrite the result field with the output of the memory stage if memop is LOAD. The actual write to the destination register will be performed in the writeback stage.

  4. Memory Seam. Just like the fetch stage, you must use your memory seam to AMO/LOAD/STORE the value since the address might be a virtual memory address needing translation.

  5. Page Faults. Page faults cannot be resolved by your virtual machine since there is no operating system on top of it. If an AMO/STORE or LOAD faults, park the HART.

    1. Restarts. The faulting HART can be restarted by using the start_hart system call.

    2. Status. The page fault can be read by the software through the hart_status system call, so it’s important to track what caused your HART to park.

The memory stage is the main source of structural stalls. On a cache miss the stage must wait while the line is fetched from a lower level (or main memory), and it must contend for the shared L3/memory locks. When memory cannot complete in one tick, stall the pipeline behind it rather than advancing with stale data. See Pipeline Hazards.

Pipeline Hazards: Stalling and Forwarding

Once you overlap five instructions all together, a later instruction may need a value that an earlier, still-in-flight instruction has not yet produced. These are pipeline hazards, and you must handle them to get correct results. There are three kinds.

Data Hazards

Recall the two-phase clock: decode reads the register file on the rising edge, and writeback writes it on the falling edge. That means a producer’s value is not visible in the register file until the end of its writeback cycle. Consider three dependent instructions:

        c1   c2   c3   c4   c5   c6
 I1 :   F    D    E    M    W
 I2 :        F    D    E    M    W
 I3 :             F    D    E    M    W

If I1 writes x5 and I2/I3 read x5, then I1 writes x5 on the falling edge of c5. But I2 reads the register file in decode on the rising edge of c3, and I3 on the rising edge of c4 (both before c5). Even an instruction decoding in c5 reads on the rising edge, before I1 writes on the falling edge. So the three instructions following a producer will read stale register values unless you do something about it. You have two tools: stalling and forwarding.

Stalling (always correct, slower)

Detect the hazard in decode: if either source register (rs1/rs2) of the instruction in decode matches the rd of any instruction currently in execute, memory, or writeback, and that rd != 0, the instruction actually writes a register, and the operand cannot use Forwarding (fast path), then stall:

  1. Freeze the program counter and the fetch/decode latch so fetch and decode present the same instructions next tick.

  2. Inject a bubble (NOP) into the decode/execute latch.

Hold the stall until the producing instruction has written back and the value is readable. This is simple to reason about and a good first implementation to validate correctness before adding forwarding.

Forwarding (fast path)

Add forwarding paths from the two most recent pipeline latches back into the execute stage’s ALU inputs:

  • From the execute/memory latch (the ALU result of the instruction one step ahead).

  • From the memory/writeback latch (the result of the instruction two steps ahead).

Just before the ALU runs, for each source operand:

  1. If the execute/memory instruction has rd == rs, and rd != 0 and it writes a register, use its result.

  2. Else if the memory/writeback instruction has rd == rs, use its result.

  3. Else use the value read from the register file.

The nearer source (execute/memory) has priority because it is the most recent producer.

Forwarding reads other stages' latches, so it must read the stable "current" latches during the rising edge. You never read a "next" buffer another stage is writing. With the two-phase barrier this is automatic. All "current" latches are frozen during the rising edge.

The Load-Use Hazard

A LOAD does not have its value until after the memory stage. If the very next instruction needs that loaded value, forwarding cannot deliver it in time, and the data simply does not exist yet when the consumer reaches execute. You must stall exactly one cycle, then forward from the memory/writeback latch.

You can detect it in decode. The instruction in execute is a LOAD (memop is a load) and its rd matches the rs1 or rs2 of the instruction in decode. When detected, insert one bubble and freeze fetch/decode for one tick.

Control Hazards (branches and jumps)

Branch taken/not taken is resolved in the EX stage. So, for a branch/jump:

  1. Compute taken/not-taken. from the NZCV flags (branch) or force taken (JAL/JALR).

  2. Compute the actual target.

  3. Compare taken and target. against what the predictor guessed in fetch.

    1. If they differ, you have a misprediction. Then do:

      1. Squash the instructions currently in IF and ID (turn them into bubbles).

      2. Redirect the PC (fetch) to the correct target next cycle.

      3. Update the branch predictor / BTB with the real outcome.

    2. If they match then speculation was correct, do nothing.

Structural Hazards

Two instructions may need the same resource in the same tick, which is most commonly the shared L3 cache or main memory, or a cache miss that cannot complete in one tick. Handle these by stalling the requesting HART’s pipeline (freeze the front end and bubble the affected latch) until the resource is available, using the locks described in Multithreading and Locking. Do not advance a stage with data it has not actually received.

Implementing Bubbles and Stalls

  • Bubble. There is no real NOP instruction, but instead, RISC-V chooses an instruction without side-effects, such as ADDI x0, x0, 0 = 0x00000013. It has rd = 0, memop = 0, and produces no register, memory, or PC side effects.

  • Stall / freeze. Do not advance the PC, do not overwrite the frozen stage’s input latch so it presents the same instruction next tick, and load the downstream latch with a bubble so the rest of the pipeline keeps draining.

Data and control hazards are per-HART concerns. Each HART has its own pipeline, register file, and predictor, so one HART’s hazards never involve another HART’s registers. Cross-HART correctness is instead a memory-ordering concern, handled by the cache-coherency protocol and by making AMO instructions atomic (see Multithreading and Locking).

The Memory Seam

The single most valuable structural idea in this project is to make all memory traffic go through one narrow interface, then layer the subsystems behind that interface:

stage   ↦  MMU (translate)   ↦  cache hierarchy (L1 → L2 → L3)   ↦  physical RAM

  • Build the layers bottom-up: raw RAM first, then drop the cache in front of it, then address translation in front of that. Each layer honors the same read/write contract, so adding one never changes a caller.

  • Recall that loads, stores, AND instruction fetches may all use cache.

  • Your configuration switches are designed to let you disable upper layers for debugging: -cL 0 bypasses the cache, -mmu off forces BARE mode, -tlb 0 disables the TLB. Keep those bypass paths working the whole semester. A correctness bug is far easier to localize when you can turn caching and translation off and confirm the pipeline still produces the right answer.

The Weakest Link: Memory Speed

Return a latency as a cycle count as well as data from the memory interface. The pipeline can use that number to decide how many cycles to stall (see Pipeline Hazards). Building this early means the cache and memory can run slower later without any change to how stages stall.

Correctness Before Microarchitecture

Everything the cache, branch predictor, TLB, and MMU add is timing and statistics, never a change to what the program computes. Use that fact. Reach a functionally correct machine first, then layer performance features on top of a design you can already trust.

A milestone order that keeps you out of trouble:

  1. Functional core (golden reference). A single-instruction-at-a-time loop: fetch, decode, execute, memory, writeback, no overlap, no threads. Wrong Turns to Avoid

These shortcuts feel fine early and quietly cripple you later:

  • Poking raw memory from a stage. Bypasses the seam between the pipeline stages and where the cache/TLB/MMU must live. Always go through the memory interface.
